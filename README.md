# Instant Virtual AI Predictor

A standalone, full-stack starter project for analyzing virtual-match screenshots and tracking prediction performance. It is separate from NexusBet.

## Features
- Responsive React/Vite web app (phone-friendly), with create-account, login, and logout screens. Users can register and log in with either an email address or a phone number; phone numbers are normalized for matching. Password minimum is 5 characters.
- Account records use salted PBKDF2-HMAC-SHA256 password hashes; bearer sessions are stored server-side. Each account's prediction history is isolated.
- Screenshot upload and camera capture (`capture="environment"` where supported).
- Browser-side OCR with Tesseract.js; extracted text can be reviewed and corrected.
- Manual match entry for teams, score, timer, and optional odds.
- FastAPI backend with SQLite storage for scans, predictions, and settled historical results.
- Probability estimates for Home / Draw / Away plus Over/Under and Both Teams To Score estimates when enough historical data is available.
- Optional Live Match Tracker: create live/upcoming/finished match cards, update scores and clocks manually, remove tracked matches, and send a tracked match into the analyzer. Tracker records are saved per account.
- Results history and simple accuracy tracking.
- Paid prediction packages: GH₵300/3, GH₵500/4, GH₵700/5, GH₵1,000/6, GH₵1,500/8, and GH₵2,000/VIP unlimited predictions.
- Manual payment request workflow for regular user accounts; scan/prediction access is blocked until the backend approves payment. Super Admin, Admin, and Sub-Admin accounts receive complimentary unlimited access and do not need to pay.
- The owner-provided payment destinations are prefilled as defaults: MTN MoMo 0558559878 (Godfred Fosu Gyan), Telecel Cash 0509623244 (Godfred Fosu Gyan), and bank account 1011103552151 (Godfred Fosu Gyan). The bank name and branch were not provided, so those fields remain blank until configured. Environment variables can override these defaults. Set `PAYMENT_ADMIN_KEY` to a long random secret and use the `X-Admin-Key` header for `/api/admin/payment-requests` review endpoints. Approve requests only after independently verifying the transaction.
- Predictions are confidence-ranked estimates, not guaranteed outcomes. The initial model is a transparent baseline, not a trained model or evidence of predictive edge.

## Requirements
- Node.js 18+ and npm
- Python 3.10+

## Run backend
From the project root:

```bash
cd backend
python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS/Linux:
source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

API docs: http://127.0.0.1:8000/docs

## Run frontend
In a second terminal:

```bash
cd frontend
npm install
npm run dev
```

Open the URL printed by Vite (usually http://localhost:5173).

The live tracker does not have a SportyBet real-time feed connected. Enter or update scores from a confirmed source; the tracker never invents live scores. You can skip it and go directly to Scan & Predict.

The frontend expects the API at `http://127.0.0.1:8000` by default. Set `VITE_API_BASE_URL` in `frontend/.env` if needed.

## Account notes
- Accounts are local to this installation and stored in SQLite. Registration and login accept an email address or phone number in the same identifier field. Phone-only accounts use an internal database alias to remain compatible with existing SQLite databases; the alias is not shown to the user. There is no email verification or password-reset flow in this starter version.
- For a public deployment, configure HTTPS, rate limiting, backups, a stronger session-expiry/revocation policy, and a production database before accepting real users.

## Important data notes
- Screenshot OCR runs in the browser through Tesseract.js. OCR can misread text; always verify extracted fields.
- The starter model uses a smoothed historical baseline and transparent fallback priors. It does not access SportyBet private systems, scrape protected services, or know future virtual-match outcomes.
- Virtual match outcomes may be random or generated by proprietary systems. More historical data does not automatically make future outcomes predictable.
- Record actual final results after a match settles. The app uses these results to report retrospective calibration/accuracy; do not treat a small sample as proof of an edge.
- Do not use this starter as a betting guarantee or risk-free strategy.

### Strongest Estimated Opportunities
The results screen ranks the currently available markets by estimated probability and displays every probability transparently. This is a probability ranking, not a claim of guaranteed outcomes or betting value. Evidence/sample warnings are shown, and the interface explains that goal-market estimates use the app's own settled-match history or broad fallback priors.

## Staff roles, referrals, and production configuration

The API now supports `super_admin`, `admin`, `sub_admin`, and `user` roles, staff referral codes, signup referral capture, a staff list/create/remove workflow, sub-admin commission ledger reporting, payout-account settings, demo-balance credit logs, and super-admin-only deposit archiving. These are backend endpoints. Approved manual prediction-package payments are written to `deposit_ledger` so Sub-Admin commission reports can include verified referred-user deposits.

### Referral links

Staff links are generated from the frontend's current origin as `/signup?ref=CODE`. A `ref` query parameter opens registration and prefills/locks the referral field. The API validates that the code belongs to staff before accepting registration. `PUBLIC_BASE_URL` is available for backend-generated links and should be set to the public frontend origin in production.

### Bootstrap the first Super Admin

Set `SUPER_ADMIN_EMAIL`, `SUPER_ADMIN_PASSWORD` (at least 5 characters), and optionally `SUPER_ADMIN_NAME` as hosting environment variables before starting the backend. Never use public registration to grant staff roles. Remove or rotate the bootstrap password after first use. The backend bootstrap promotes an existing matching account or creates the initial Super Admin on startup.

### Production environment

- Set `VITE_API_BASE_URL` in the frontend build environment to the deployed FastAPI URL.
- Set `CORS_ORIGINS` to a comma-separated list of exact trusted frontend origins (no wildcard when credentials are needed).
- Set `PUBLIC_BASE_URL` to the canonical public frontend origin, e.g. `https://your-real-domain.example`.
- Set payment destination values and a long random `PAYMENT_ADMIN_KEY` in the backend hosting environment; do not commit production secrets.
- Use HTTPS, a persistent database volume or managed database, backups, request rate limiting, and monitored audit logs before public production use.

### Admin endpoint notes

- `POST /admin/users/create-staff`, `GET /admin/staff/manage`, `DELETE /admin/staff/manage/{id}`
- `GET /admin/referrals/ledger` (sub-admin only)
- `GET /admin/payout-settings` (admin/super-admin), `POST /admin/payout-settings` (super-admin only)
- `POST /admin/users/credit-demo` (role-scoped; sub-admins can credit only their own referred users)
- `DELETE /admin/deposits/clear-older?days=90` (super-admin only; archives before deleting)

Important limitation: manual payment review still uses the separate `PAYMENT_ADMIN_KEY` workflow rather than staff JWT roles. Approved package payments are written into the referral deposit ledger, but you should test staff permissions and payment review end-to-end before production use.

### Local Super Admin setup (VS Code)

1. In `backend`, copy `.env.example` to a file named `.env`.
2. Set `SUPER_ADMIN_EMAIL` to the email address you want to use for the first Super Admin and set `SUPER_ADMIN_PASSWORD` to a password of at least 5 characters.
3. Install backend requirements again after this amendment with `python -m pip install -r requirements.txt`.
4. Restart the backend. On startup, the app creates the first Super Admin if that email does not already exist. Log in with that exact email and password. Do not use public registration to create staff accounts.
5. To create Admins or Sub-Admins, log in as Super Admin and use the staff management section.

The login form accepts an email address or phone number. If an error appears, it will now display a readable server validation message instead of `[object Object]`.
